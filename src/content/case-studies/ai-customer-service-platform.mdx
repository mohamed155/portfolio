decisions:
  - n: 'decision 01 · adr-001'
    problem: 'Around twenty bounded contexts and one small team. Microservices would buy independent deployment at the price of a distributed system to operate.'
    decision: 'A modular monolith: one deployable and one database, with each domain a separate crate that exposes a facade and its event types.'
    reason: 'The compiler enforces the module boundaries, a transaction can span modules when it must, and the seams are already cut if a module ever needs extracting.'
    tradeoff: 'One release train for everything, and a dependency cycle is a hard compile error — notification emits are written by hand in three modules because the shared helper would close a cycle.'
  - n: 'decision 02 · adr-004'
    problem: 'Tenants share a database. Schema-per-tenant multiplies every migration; database-per-tenant multiplies the operations.'
    decision: 'Shared schema with a tenant_id column, tenant-scoped transactions and PostgreSQL Row-Level Security.'
    reason: 'The database refuses a cross-tenant read even when application code forgets the filter, and one schema means one migration path for every tenant.'
    tradeoff: 'The application must connect as a role that cannot bypass RLS, which needs its own verification script, and every tenant index leads with tenant_id.'
  - n: 'decision 03 · adr-007'
    problem: 'State changes and the events they cause were at risk of drifting apart, and a message broker would be one more system to run and reason about.'
    decision: 'A transactional outbox and a job queue, both in PostgreSQL. The event row commits in the same transaction as the state it describes.'
    reason: 'No lost or phantom events, no new infrastructure, and the queue is covered by the same backup as the business data.'
    tradeoff: 'Delivery is at-least-once, so every consumer has to be idempotent, and very hot queues would eventually need moving to a dedicated broker.'
  - n: 'decision 04 · adr-010'
    problem: 'Public widget and webhook traffic shared a process with the authenticated dashboard API and the background workers.'
    decision: 'One binary and one composition root with run modes: api, gateway, worker, and all for local development.'
    reason: 'Untrusted traffic is isolated and each unit scales on its own signal, while the codebase, the build and the tests stay single.'
    tradeoff: 'Route and worker sets must be kept honest per mode, and a deployment now has three units to roll out and probe instead of one.'
